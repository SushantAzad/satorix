INFRACORE FOUNDRY — COMPLETE COMMERCIAL, TECHNICAL & PRODUCT READINESS AUDIT                                                                    
                                                                                                                                                  
  ---                                                                                                                                             
  PHASE 1 — CURRENT SYSTEM CAPABILITY AUDIT                                                                                                       
                                                                                                                                                  
  What The Platform Actually Is                                                                                                                   
                                                                                                                                                  
  This is a six-layer data intelligence pipeline with a graph knowledge base at the center, built specifically for Indian corporate intelligence. 
  It is architecturally ambitious, well-structured, and has significantly more working code than most projects at this stage. Total
  implementation: ~35,600 Python lines across 6 layers plus 3 React frontends.                                                                    
                                                            
  Here is the honest breakdown by capability:                                                                                                     
  
  ---                                                                                                                                             
  Ingestion Capabilities — Fully Working                    
                                                                                                                                                  
  Eleven connectors exist and all have real network I/O:
                                                                                                                                                  
  - CSV, Excel, PDF (digital + OCR via Tesseract with Hindi support)                                                                              
  - REST API (5 auth methods, 5 pagination strategies, exponential backoff)                                                                       
  - MySQL, S3, SFTP, Google Sheets, Webhook                                                                                                       
  - MCA21 (Sandbox.co.in API + bulk download, Redis-cached), RBI master data, SEBI enforcement orders, TallyPrime (live XML + offline export)
                                                                                                                                                  
  The sync engine is production-grade: PostgreSQL advisory locking prevents duplicate runs, deterministic batch IDs for idempotency, watermark    
  tracking, schema fingerprinting, data profiling on every batch, Kafka notification with Redis fallback. This is genuinely good work.            
                                                                                                                                                  
  One lie in the system: Tally.get_record_count() returns hardcoded 0. One stub. Everything else has real implementations.                        
  
  Verdict: Production-capable ingestion layer.                                                                                                    
                                                            
  ---
  Graph Intelligence Capabilities — Partially Working
                                                                                                                                                  
  The core Neo4j graph layer works:
                                                                                                                                                  
  - 11 node types: Company, Director, Project, RegulatoryAction, LegalCase, InsolvencyProceeding, Address, RegulatoryBody, GovernmentEntity,      
  Event, Alert
  - 20+ relationship types with proper semantic definitions                                                                                       
  - BFS network traversal up to configurable depth          
  - Betweenness centrality, PageRank, Louvain community detection                                                                                 
  - Shortest path computation
  - Subgraph extraction, diffing, and export (GraphML, D3, Cytoscape)                                                                             
  - Temporal network analysis                                                                                                                     
                                                                                                                                                  
  What doesn't work in production:                                                                                                                
  - The natural language query parser is a stub — it parses intent but delegates the actual query composition incompletely
  - The graph has no client isolation whatsoever. Every entity in Neo4j is global. If you onboard two clients, their data mingles. This is the    
  single most dangerous architectural gap in the system.                                                                                      
                                                                                                                                                  
  Verdict: Core graph operations work. Client isolation is missing.
                                                                                                                                                  
  ---                                                       
  Ontology Capabilities — Fully Working                                                                                                           
                                                            
  The ontology layer is genuinely solid:
                                                                                                                                                  
  - All 11 entity types have formal semantic definitions with typed properties
  - Schema registry with versioning                                                                                                               
  - Relationship validation against defined link types                                                                                            
  - Schema drift detection via fingerprinting
  - Orphan detection, duplicate surface detection, impossible-state checking                                                                      
  - Full Elasticsearch indexing for text search                                                                                                   
  - Object data funnel for multi-source entity merging                                                                                            
                                                                                                                                                  
  Verdict: The ontology design is production-grade.                                                                                               
                                                                                                                                                  
  ---                                                                                                                                             
  Search Capabilities — Fully Working                       
                                     
  Elasticsearch-backed full-text search with:
  - Cross-entity type search (companies, directors, projects simultaneously)                                                                      
  - CIN/DIN/RERA identifier extraction and normalization                    
  - Risk score and flag aggregation in results                                                                                                    
  - Layer 6 normalization handling both Elasticsearch and Palantir response formats                                                               
                                                                                                                                                  
  Verdict: Works.                                                                                                                                 
                                                                                                                                                  
  ---                                                                                                                                             
  AI Enrichment Capabilities — Prototype-Level              
                                                                                                                                                  
  This is the most nuanced part of the assessment:
                                                                                                                                                  
  What actually works:                                                                                                                            
  - LLM orchestration (Anthropic + Ollama) with prompt caching, audit logging, RBAC, Redis response cache — this code is solid
  - 7 prompt templates for due diligence, CIRP explanation, regulatory extraction, entity intelligence, Q&A                                       
  - Report generation assembling L3 data + L4 network + LLM narrative into a structured document           
  - CIRP risk explanation with SHAP feature attribution — when SHAP values exist                                                                  
                                                                                                                                                  
  What is prototype-level:                                                                                                                        
  - The CIRP "ML model" is a deterministic rule-based heuristic scoring system, not a trained model. There are no model artifacts. The            
  ModelServingEngine has full infrastructure to load pickle files from MinIO — but no champion model is registered. It falls back to heuristic    
  scoring 100% of the time. The system acknowledges this with comments like "Phase 2: XGBoost trained on labeled CIRP cases (switch when 50+  
  examples available)."                                                                                                                           
  - SHAP explanations return None because TreeExplainer requires an actual tree model, not heuristics.
  - Feature store exists but is populated from whatever L3/L4 data exists — no curated feature pipeline.
                                                                                                                                                  
  Verdict: The LLM enrichment works. The "ML predictions" are rule-based heuristics wearing ML clothing. This distinction matters enormously for  
  enterprise clients who will ask about model validation.                                                                                         
                                                                                                                                                  
  ---                                                                                                                                             
  Streaming/Event Capabilities — Working Infrastructure, Thin Logic
                                                                                                                                                  
  Kafka consumers exist in Layers 1, 3, and 6. Micro-batching works. The alert trigger stream exists. WebSocket real-time updates are wired in
  Layer 6. However:                                                                                                                               
                                                            
  - No dead letter queue handling                                                                                                                 
  - No offset management or consumer lag monitoring         
  - Alert routing logic is basic                                                                                                                  
  - No backpressure handling under volume
                                                                                                                                                  
  Verdict: Works at demo scale. Needs hardening for production volume.                                                                            
                                                                                                                                                  
  ---                                                                                                                                             
  Reporting Capabilities — Partially Working                
                                            
  The due diligence report generator is genuinely interesting — it assembles:
  1. Entity profile from Layer 3                                                                                                                  
  2. Network from Layer 4                                                                                                                         
  3. CIRP prediction (heuristic)                                                                                                                  
  4. LLM explanation of risk                                                                                                                      
  5. Benchmark comparison                                   
  6. Trend analysis                                                                                                                               
  7. LLM executive summary
                                                                                                                                                  
  The output is a structured JSON that gets persisted to PostgreSQL and cached in Layer 6. The report format is solid.
                                                                                                                                                  
  What's missing: PDF/Word export, branded templates, downloadable documents. Everything stays as JSON. An enterprise client expecting a          
  deliverable report needs a rendered document, not raw JSON.                                                                                     
                                                                                                                                                  
  Verdict: Report assembly works. Presentation layer for the report doesn't exist.

  PHASE 2 — DATAFLOW ANALYSIS                               
                             
  Complete End-to-End Flow
                                                                                                                                                  
  CLIENT DATA
      │                                                                                                                                           
      ▼                                                     
  LAYER 1 — INGESTION (Port 8001)
      │
      │  Input: CSV / Excel / PDF / REST API / MySQL / Tally / MCA21 / SEBI
      │                                                                                                                                           
      │  What happens:
      │  1. Source registered in PostgreSQL (data_sources table, AES-256-GCM encrypted creds)                                                     
      │  2. Sync triggered: advisory lock acquired, batch_id generated (deterministic hash)                                                       
      │  3. Connector extracts records → data profiled (nulls, distributions, anomalies)                                                          
      │  4. Records written to MinIO as Parquet (raw-data bucket, partitioned by source/date)                                                     
      │  5. SyncState watermark updated in PostgreSQL                                                                                             
      │  6. Kafka event published: "batch_ready" → Layer 2                                                                                        
      │                                                                                                                                           
      │  PostgreSQL tables: data_sources, sync_states, sync_runs, data_source_health                                                              
      │  MinIO: s3://raw-data/{client_id}/{source_id}/{date}/{batch_id}.parquet                                                                   
      │                                                                                                                                           
      ▼                                                                                                                                           
  LAYER 2 — TRANSFORMATION (Port 8002)                                                                                                            
      │                                                     
      │  Input: Kafka "batch_ready" event with MinIO path
      │                                                                                                                                           
      │  What happens:
      │  1. DAG definition loaded (YAML pipeline config)                                                                                          
      │  2. Topological sort determines execution order                                                                                           
      │  3. Transform steps execute sequentially:                                                                                                 
      │     - String cleaning, date parsing, number normalization                                                                                 
      │     - CIN/DIN/RERA identifier normalization with check-digit validation                                                                   
      │     - Indian address normalization (PIN codes, state codes)                                                                               
      │     - Deduplication (exact + fuzzy via rapidfuzz)                                                                                         
      │     - Entity resolution across batches                                                                                                    
      │  4. Transformed records written to MinIO (processed-data bucket)                                                                          
      │  5. Lineage recorded in PostgreSQL                                                                                                        
      │  6. Kafka event: "records_transformed" → Layer 3                                                                                          
      │                                                                                                                                           
      │  PostgreSQL tables: l2_pipeline_runs, l2_transform_steps, l2_lineage
      │  MinIO: s3://processed-data/{pipeline_id}/{run_id}/output.parquet                                                                         
      │                                                                                                                                           
      ▼                                                                                                                                           
  LAYER 3 — ONTOLOGY (Port 8003)                                                                                                                  
      │                                                     
      │  Input: Kafka "records_transformed" event
      │                                                                                                                                           
      │  What happens:
      │  1. Object mapper maps transformed records to semantic entity types                                                                       
      │  2. Schema validator checks against registered ontology definitions                                                                       
      │  3. Entity upserted into Neo4j (MERGE on primary key: CIN/DIN/RERA)
      │  4. Entity properties stored in PostgreSQL (l3_objects table)                                                                             
      │  5. Entity indexed in Elasticsearch for full-text search                                                                                  
      │  6. Relationships derived and created in Neo4j                                                                                            
      │  7. Risk scoring computed (rule-based, stored on node)                                                                                    
      │  8. Kafka event: "entity_upserted" → Layer 4                                                                                              
      │                                                                                                                                           
      │  Neo4j: Nodes (11 types) + Relationships (20+ types), global (no client isolation)                                                        
      │  PostgreSQL: l3_objects, l3_relationships, l3_events, l3_alerts                                                                           
      │  Elasticsearch: one index per entity type                                                                                                 
      │                                                                                                                                           
      ▼                                                                                                                                           
  LAYER 4 — GRAPH INTELLIGENCE (Port 8004)                  
      │                                                                                                                                           
      │  Input: API calls from Layer 5/6 OR background batch jobs (Airflow)
      │                                                                                                                                           
      │  What happens:                                      
      │  1. Network traversal: BFS up to depth 3 from any entity                                                                                  
      │  2. Centrality computation: betweenness + PageRank + influence composite                                                                  
      │  3. Cluster detection: Louvain community detection on director/address networks                                                           
      │  4. Shared attribute detection: common directors, addresses, regulatory actions                                                           
      │  5. Path scoring: shortest paths with risk-weighted edges                                                                                 
      │  6. Influence scores persisted to PostgreSQL (l4_influence_scores)                                                                        
      │                                                                                                                                           
      │  PostgreSQL: l4_influence_scores, l4_cluster_members, l4_path_cache                                                                       
      │  Neo4j: read-only traversals, no writes from L4                                                                                           
      │                                                                                                                                           
      ▼                                                                                                                                           
  LAYER 5 — ANALYTICS & AI (Port 8005)                                                                                                            
      │                                                     
      │  Input: API calls from Layer 6
      │                                                                                                                                           
      │  What happens:
      │  1. Feature store consulted for entity features                                                                                           
      │  2. Model serving: heuristic fallback (no trained models exist yet)
      │  3. LLM call via OllamaProvider/AnthropicProvider → qwen3:8b / claude-sonnet                                                              
      │  4. Response cached in Redis (SHA-256 keyed, configurable TTL)                                                                            
      │  5. All LLM calls audit-logged in PostgreSQL (l5_llm_audit)                                                                               
      │  6. Report assembled, persisted to l5_reports                                                                                             
      │                                                                                                                                           
      │  PostgreSQL: l5_predictions, l5_reports, l5_llm_audit, l5_scenarios, l5_model_registry                                                    
      │                                                                                                                                           
      ▼                                                     
  LAYER 6 — DASHBOARD (Port 8006 + 3000/3001/3002)                                                                                                
      │                                                                                                                                           
      │  Input: User interaction via React frontend
      │                                                                                                                                           
      │  What happens:                                      
      │  1. JWT auth against l6_users table
      │  2. Aggregators call L3/L4/L5 via httpx clients                                                                                           
      │  3. Network data transformed to Cytoscape.js format for visualization                                                                     
      │  4. Risk scores, alerts, operational metrics assembled                                                                                    
      │  5. Reports fetched and cached in l6_report_cache (24h TTL)                                                                               
      │  6. Real-time updates via Kafka consumer → WebSocket broadcast                                                                            
      │                                                                                                                                           
      │  PostgreSQL: l6_users, l6_watchlists, l6_report_cache, l6_recent_views                                                                    
                                                                                                                                                  
  Critical observation: The .env file configures all service URLs as localhost. Inside Docker containers, inter-service communication must use    
  Docker service names (postgres, redis, neo4j, etc.). This means the current .env cannot work inside Docker as-is — it would work if services are
   run locally (bare metal), or if the docker-compose uses network_mode: host. This needs verification before any deployment.

  PHASE 3 — CLIENT DATA ONBOARDING
                                  
  How Real Data Gets In
                                                                                                                                                  
  Method 1 — CSV Upload                                                                                                                           
  Current state: Connector exists, API endpoint exists (POST /sources). Manual setup required:                                                    
  1. Admin must register the source via API (no UI wizard for this)                                                                               
  2. Schema must be manually mapped to entity types                                                                                               
  3. Transformation pipeline must be manually configured as YAML DAG                                                                              
  4. Trigger sync                                                                                                                                 
                                                            
  Assessment: Works technically. Requires a developer or technical implementer to set up. A compliance firm cannot self-onboard from CSV without  
  guidance. Onboarding time: 0.5–1 day per source type with hands-on support.                                                                     
                                                                                                                                                  
  Method 2 — REST API Integration                                                                                                                 
  Fully functional connector with 5 auth methods and 5 pagination strategies. Same manual pipeline setup required. Client must expose an API; you
  configure the connector.                                                                                                                        
                                                            
  Method 3 — Database Connectors                                                                                                                  
  MySQL connector exists. PostgreSQL would need adding (ironic — the platform itself uses Postgres). Direct DB connections require VPN or network
  access setup. This is typically the most enterprise-friendly path but also the most operationally complex.                                      
   
  Method 4 — MCA21 / SEBI / RBI                                                                                                                   
  This is the most valuable onboarding path for Indian corporate intelligence. The MCA21 connector uses Sandbox.co.in API — this requires an
  active Sandbox.co.in subscription. SEBI connector exists. RBI master data connector exists. These can be run in bulk to populate the graph with 
  public Indian company data without any client providing anything.
                                                                                                                                                  
  The real onboarding story for first clients: You would pre-populate the graph with MCA21 data (all registered companies, directors, filings) and
   let clients query what already exists. Their "onboarding" is then adding their private data (portfolio companies, internal watchlists) on top
  of a pre-built knowledge base. This is the correct commercial approach.                                                                         
                                                            
  Method 5 — TallyPrime
  Connector for Tally XML server + offline export. This is uniquely valuable for Indian SME clients who use Tally for accounting. Competitive
  differentiator if this works reliably.                                                                                                          
   
  How much manual setup is needed today: Significant. There is no self-service onboarding UI. Every new data source requires:                     
  - API calls to register the source                        
  - YAML pipeline definition                                                                                                                      
  - Manual entity type mapping                              
  - Technical resource to run and monitor                                                                                                         
                                         
  Scalability of onboarding today: Not scalable. This is a single-client, high-touch setup currently. To onboard 5+ clients simultaneously, you   
  need an onboarding UI, a pipeline template library, and documented playbooks.

  PHASE 4 — CLIENT VALUE PROPOSITION

  What this platform provides:                              
  - Pre-ingested MCA21, SEBI, RBI data eliminates most of the research phase
  - Director network mapping in seconds (who else does this director sit with, what's their history)                                              
  - Regulatory action timeline automatically assembled                                              
  - LLM-generated due diligence summary in structured format                                                                                      
  - Cross-entity risk correlation (company → directors → related companies → regulatory actions)                                                  
                                                                                                                                                  
  Traditional workflow: 2 analysts, 6 hours, deliverable in Word doc.                                                                             
  Platform workflow: 15 minutes to generate structured intelligence, analyst adds judgment layer.                                                 
                                                                                                                                                  
  This is the strongest value proposition in the portfolio. Compliance firms have budget, recurring need, and measurable time savings.            
                                                                                                                                                  
  Banks / NBFCs                                                                                                                                   
                                                            
  Problem: Loan appraisal requires manual KYC, director background, promoter history, related entity risk. Done across siloed systems.            
   
  What this platform provides:                                                                                                                    
  - Automated promoter background check: director history, disqualification status, prior CIRP involvement
  - Related party exposure: other companies controlled by same directors                                                                          
  - CIRP probability score (currently rule-based heuristic — honest limitation)
  - Network risk: if a key director sits on 3 other stressed companies, that's a signal                                                           
                                                                                                                                                  
  However: Banks have stringent data residency, RBI compliance, and vendor onboarding requirements. This is a 6–12 month sales cycle even if the  
  product is perfect. Not the right first customer.

  Similar to banks but shorter procurement cycles. NBFC-MFIs doing portfolio monitoring are a better early target than large banks.

  What this platform provides:

  - Corporate structure mapping (parent/subsidiary chains)                                                                                        
  - Director network — who is connected to whom

  - CIRP/insolvency proceeding tracking

  ---                                                                                                                                             
  PHASE 5 — PRODUCTION READINESS AUDIT                      
                                                                                                                                                  
  Scalability
                                                                                                                                                  
  Ingestion layer: Horizontally scalable in theory — async Kafka consumers, stateless connectors. In practice: no horizontal scaling configuration
   exists. Everything runs as single-process Docker containers.
                                                                                                                                                  
  Neo4j: Single instance. No clustering. For a graph with millions of nodes (all Indian companies + directors ≈ 2M+ entities), a single Neo4j     
  Community Edition instance will become a bottleneck. Neo4j Enterprise clustering is required beyond demo scale, and that carries significant
  licensing cost.                                                                                                                                 
                                                            
  PostgreSQL: Single instance. No read replicas. Multiple layers write to the same instance. Under concurrent client load, this will contend.     
   
  LLM (Ollama): Single instance. qwen3:8b on a single GPU/CPU. Each report takes 5–30 seconds depending on hardware. Five concurrent users        
  generating reports = queue starvation. No request queuing or rate limiting exists.
                                                                                                                                                  
  Verdict: Not horizontally scalable today. Fine for a single-client proof of concept. Will fail under simultaneous multi-client load.            
   
  ---                                                                                                                                             
  Fault Tolerance                                           
                 
  Circuit breaker: Implemented in Layer 1 (consecutive_failures, circuit_open fields). Only one layer has this.
                                                                                                                                                  
  Kafka failure: Layer 1 falls back to Redis notification. Layers 2–6 have no fallback if Kafka is unavailable.                                   
                                                                                                                                                  
  Layer 5 LLM failure: Has fallback text ("LLM unavailable — analyst review required"). This is correct.                                          
                                                            
  Database failure: No retry logic or connection pool failover beyond what asyncpg provides by default.                                           
                                                            
  Verdict: Basic fault tolerance exists in Layer 1. Other layers are brittle.                                                                     
                                                            
  ---                                                                                                                                             
  API Stability                                             
               
  60+ endpoints across 6 services. No API versioning beyond the /api/v1 prefix. No API changelog. No backward-compatibility guarantees. This is
  acceptable for pre-MVP but will cause pain when client integrations are built.                                                                  
   
  No rate limiting on any endpoint. A single client can saturate the API with unbounded requests.                                                 
                                                            
  ---                                                                                                                                             
  Security                                                  
          
  Critical issues:
                                                                                                                                                  
  1. JWT secret is a placeholder string in .env: change-me-in-production-use-python-secrets-token-hex-32. If deployed as-is, any attacker knowing 
  this can forge tokens for any user. This must be changed before any real deployment.                                                            
  2. CORS hardcoded to localhost only: CORS origins are ["http://localhost:3000", "http://localhost:3001", "http://localhost:3002"]. A production 
  deployment will fail CORS checks immediately. This is not a security flaw per se — it actually makes it more secure — but it means the app won't
   work from any deployed URL without code changes.
  3. No HTTPS/TLS: All services use HTTP. MINIO_SECURE=false. No SSL termination configured. Everything is plaintext in transit.                  
  4. No rate limiting: Anyone with a valid token can hammer the API without limit.                                                                
  5. No API key authentication for inter-service calls: Layer 6 calls Layer 3/4/5 without any authentication. If any layer's port is accessible on
   the network, it can be called without credentials.                                                                                             
  6. Token revocation is explicitly absent: The logout route comments "For MVP there is no server-side token revocation." A stolen JWT is valid   
  until expiry with no way to revoke it.                                                                                                          
                                                            
  Non-critical issues:                                                                                                                            
  - AES-256-GCM encryption on connector credentials in Layer 1 — this is correct
  - Bcrypt password hashing — this is correct                                                                                                     
  - Input validation via Pydantic — this is correct         
                                                                                                                                                  
  Security verdict: Not suitable for any external-facing deployment in current state. Requires TLS, proper secrets management, rate limiting, and 
  inter-service auth before any client demo on a non-localhost environment.                                                                       
                                                                                                                                                  
  ---                                                                                                                                             
  Multi-Tenancy                                             

  This is the most structurally dangerous gap in the platform.

  What exists:
  - client_id field in Layer 1 DataSource model (sources are scoped per client)
  - client_id field in l6_users table (nullable)                                                                                                  
  - No enforcement anywhere in the data path    
                                                                                                                                                  
  What is missing:                                                                                                                                
  - Neo4j has zero client isolation. All companies, directors, projects exist in the same graph without any tenant tagging. Client A can see
  Client B's private entities.                                                                                                                    
  - Layer 3 API does not filter by client_id. The search endpoint returns all entities globally.
  - Layer 4 graph traversals are global.                                                                                                          
  - Layer 5 predictions and reports are not scoped to a client.                                                                                   
  - The l6_report_cache table has user_id but this is a user-level cache, not tenant-level isolation.                                             
                                                                                                                                                  
  The implication: This is designed as a single-tenant shared knowledge base (where all the "data" is public MCA21/SEBI data shared by everyone). 
  If you want to let Client A and Client B have private data that the other cannot see, that architecture does not exist yet.                     
                                                                                                                                                  
  For the first use case (shared public Indian corporate data accessed by all clients), this is acceptable. The moment a client wants to add their
   own private watchlists, portfolio data, or internal annotations, you have a tenant isolation problem.
                                                                                                                                                  
  Verdict: Single-tenant or shared-public-data architecture only. True multi-tenancy requires architectural work on Neo4j (separate databases per 
  tenant or property-based filtering enforced everywhere).
                                                                                                                                                  
  ---                                                       
  Monitoring
            
  - No application performance monitoring (APM) configured — no Prometheus metrics, no Datadog, no OpenTelemetry
  - No health check aggregation dashboard                                                                                                         
  - No alerting on service downtime                                                                                                               
  - No error rate tracking across services                                                                                                        
  - LLM calls are audit-logged (good) but there's no operational dashboard showing failure rates                                                  
                                                                                                                                                  
  Layer 6 operational dashboard shows data quality metrics pulled from Layer 1/3 — but this is a business dashboard, not an infrastructure        
  monitoring tool.                                                                                                                                
                                                                                                                                                  
  Verdict: No production monitoring. You would not know if Layer 4 is down until a user reports an empty graph.

  Test Coverage                                             
               
  11 test files for a 35,600-line codebase. That's approximately one test file per 3,200 lines of code. Tests exist for: CSV connector, identifier
   normalization, consistency rules, profiling, encryption, risk scoring, ontology workflow, incremental indexer, LLM provider.                   
   
  Verdict: Test coverage is critically low. Core business logic (graph intelligence, report generation, LLM workflows) has essentially zero test  
  coverage.

  PHASE 6 — MVP STRATEGY
                                                                                                                                                  
  What To Include In MVP
                                                                                                                                                  
  Layer 1 (Ingestion): Keep MCA21, CSV, REST connectors. Drop SFTP, Google Sheets, MySQL for now. The Tally connector is a differentiator — keep  
  it.
                                                                                                                                                  
  Layer 2 (Transformation): Keep CIN/DIN normalization, deduplication, identifier validation. Drop the full DAG engine complexity — simplify to a 
  linear pipeline for MVP.
                                                                                                                                                  
  Layer 3 (Ontology): Keep Company, Director, RegulatoryAction, InsolvencyProceeding node types. Drop Project, GovernmentEntity, Event, Alert for

  How to tier the 11 connectors by priority:
                                                                                                                                                  
  Tier 1 — Build UI first (weeks 1–2):
  - CSV / Excel / PDF — drag-and-drop upload, column mapper, entity type selector. This is the universal onboarding path. Every client has

  - REST API — needs a proper multi-step wizard (endpoint URL → auth method → pagination config → field mapping → test call). This is

  - TallyPrime — requires explaining to the client how to expose their Tally XML server, which is a support conversation, not a self-service UI.

  Tier 3 — Ship with minimal UI or skip for now:
  - MySQL / SFTP / S3 — only enterprise clients with technical teams need these. A connection string form plus a test button is sufficient for

  - RBI / SEBI — these are background system connectors you run, not something clients configure. They don't need client-facing UI.               
  - Webhook — needs documentation more than UI. Advanced use case.                                                                 
                                                                                                                                                  
  ---                                                                                                                                             
  The design pattern to follow:                                                                                                                   
                                                                                                                                                  
  Look at how Airbyte and Fivetran handle connector setup — a consistent 3-step wizard: (1) configure credentials, (2) test connection, (3)
  configure what to sync. Every connector uses the same shell, only the fields inside change. This is the right pattern because it makes all 11   
  connectors feel like one product rather than 11 different tools.
                                                                                                                                                  
  The column-mapping step (after connection) is where you add specific value over generic ETL tools — because you're mapping to your ontology     
  (Company, Director, Project), not just moving data. That screen needs to be designed carefully. Showing a side-by-side preview ("your column
  company_name → maps to Company.name") with a live sample row builds trust immediately.
