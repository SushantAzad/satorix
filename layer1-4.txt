  1. SYSTEM OVERVIEW                                                                                                                              
                                                                                                                                                  
  What it actually does:                                                                                                                          
  Satorix is a data intelligence platform built for Indian corporate entity analysis. It ingests raw structured data from multiple sources (MCA21,
   SEBI, RBI, CSV, APIs), cleans and normalises it through declarative YAML pipelines, maps it into a typed ontology graph, and computes risk     
  scores, community clusters, influence centrality, and CIRP (insolvency) precursor signals across the entity graph.                              
                                                                                                                                                  
  Problems it solves:                                                                                                                             
  - Ingesting and deduplicating messy Indian regulatory data (CIN, DIN, GSTIN, PAN normalisation)                                                 
  - Detecting cross-entity risk through shared director/address/ownership patterns                                                                
  - Predicting CIRP risk before insolvency filings using graph signals                                                                            
  - Producing graph-traversal-based connection paths between corporate entities                                                                   
  - Maintaining a versioned, lineage-tracked record of every data transformation                                                                  
                                                                                                                                                  
  Current maturity: 4 layers fully coded and importable. Infrastructure (Kafka, Neo4j, Elasticsearch) required for runtime — not currently        
  running. System test passes 128/128 checks against local Python logic.

  2. LAYER-WISE BREAKDOWN                                   
                         
  Layer 1 — Data Ingestion
                                                                                                                                                  
  Port: 8001
  Purpose: Extract raw data from sources, profile quality, land as Parquet in MinIO, notify downstream.                                           
                                                                                                                                                  
  Implemented components:
  - FastAPI API (api/app.py) — v0.2.0, 4 route groups: sources, sync, health, webhooks                                                            
  - 10 generic connectors — CSV, Excel, PDF, Google Sheets, MySQL, REST API, S3, SFTP, Webhook + base class                                       
  - 4 Indian-specific connectors — MCA21, RBI, SEBI, Tally                                                 
  - Data profiler (profiling/profiler.py) — produces ProfileReport with per-column quality analysis (completeness, uniqueness, pattern            
  conformance, anomalies, distribution)                                                                                                           
  - 13 domain consistency rules — PaidUpCannotExceedAuthorized, IncorporationDateNotFuture, CIRPCompanyFinancials, DebtEquityEqualsCost, etc.     
  - Indian identifier validators — CIN, DIN, GSTIN (pattern), PAN, IFSC, PIN, Mobile with validate_cin(), validate_pan(), validate_din(),         
  validate_gstin() standalone functions                                                                                                           
  - Schema detector/normaliser/type inferrer — auto-detects Indian identifier columns by sampling                                                 
  - Sync engine (sync/sync_engine.py) — publishes layer1.raw.parquet.ready to Kafka (primary) and Redis LPUSH (fallback)                          
  - Kafka publisher (streaming/kafka_producer.py) — KafkaEventPublisher, lazy-init, acks=all, non-fatal on failure                                
  - State manager — high-water mark incremental sync tracking                                                                                     
  - Batch ID generation — SHA-256(source_id + sync_type + hour_partition)[:16], deterministic                                                     
  - Airflow DAG — extraction_dag.py                                                                                                               
  - DB migrations — 2 SQL files (source registry schema)                                                                                          
  - API key auth — optional, warns on startup if not set                                                                                          
                                                                                                                                                  
  Inputs: CSV, Excel, PDF, MySQL, REST APIs, Google Sheets, S3, SFTP, webhooks, MCA21/RBI/SEBI regulatory feeds                                   
  Outputs: Parquet files in MinIO (raw-data/ bucket), layer1.raw.parquet.ready Kafka event, Redis queue fallback

  Layer 2 — Transformation Pipeline                                                                                                               
                                                                                                                                                  
  Port: 8002
  Purpose: Execute declarative YAML pipelines on raw Parquet — clean, validate, deduplicate, enrich, output processed Parquet.                    
                                                                                                                                                  
  Implemented components:
  - FastAPI API (api/app.py) — 4 route groups: pipelines, runs, errors, lineage                                                                   
  - PipelineExecutor (core/executor.py, 635 lines) — reads Parquet from MinIO → parses DAG → executes steps in topological order → writes         
  processed Parquet → persists run state                                                                                                 
    - Deterministic run_id: SHA-256(pipeline_id:version:input_batch_id)[:16]                                                                      
    - Idempotency: skips already-completed runs                             
    - PostgreSQL advisory lock: prevents concurrent runs for same pipeline/batch                                                                  
    - Cross-batch deduplication: wired pre-transform, 90-day lookback                                                                             
    - Publishes layer2.clean.ready to Kafka on completion                                                                                         
  - PipelineDAG (core/dag.py) — parses YAML, topological sort (networkx or DFS fallback), cycle detection, critical path computation              
  - 28+ transform classes in 3 categories:                                                                                                        
    - Cleaning: TrimWhitespace, NormalizeCase, NormalizeCIN, NormalizeGSTIN, NormalizePAN, NormalizeDIN, NormalizeIFSC, ParseIndianDate,          
  ComputeFinancialYear, ComputeAge, DateDifference, ExtractPINCode, NormalizeState, NormalizeCity, SplitAddressComponents, RegexExtract,          
  RegexReplace, FillNullString, RemoveSpecialCharacters                                                                                           
    - Structural: RenameColumns, DropColumns, SelectColumns, AddComputedColumn, AddConstantColumn, SplitColumn, ConcatColumns, CastColumn,        
  InnerJoin, LeftJoin, Union, Aggregate, Pivot, Unpivot, Lookup                                                                                   
    - Enrichment: reference lookups (state, PIN code, NIC code, IFSC)                                                                             
  - DataQualityValidator — applies QualityRule objects: not_null, not_empty, regex/regex_match, range, in_set, custom_expr, referential; 4 failure
   policies: reject, flag, default, transform                                                                                                     
  - Deduplicator — ExactDeduplicator (key-column drop-dup), FuzzyDeduplicator (rapidfuzz, threshold), CrossBatchDeduplicator (SHA-256[:16]        
  fingerprints persisted in l2_batch_fingerprints)                                                                                                
  - Cross-batch dedup storage — l2_batch_fingerprints table, unique index on (pipeline_id, fingerprint), 90-day lookback, capped at 50,000        
  fingerprints per run                                                                                                                    
  - LineageTracker — field-level lineage events per transform step                                                                                
  - QuarantineManager — bad records go to quarantine table with error classification
  - Error classifier — classifies errors as source, transform, or system                                                                          
  - Airflow DAG (layer2_pipeline_dag.py) — polls every 15 minutes; priority: Kafka → Redis → DB discovery; retries 2× with exponential backoff,   
  max 4 concurrent runs                                                                                                                           
  - Pipeline definitions — 2 YAML files: company_master.yaml (20-step pipeline for MCA21 data), director_mapping.yaml                             
  - DB migrations — 3 SQL files: pipeline definitions, pipeline runs/step-runs, batch fingerprints                                                
                                                                                                                                                  
  Inputs: Parquet files from MinIO (Layer 1 output), layer1.raw.parquet.ready Kafka/Redis events                                                  
  Outputs: Processed Parquet in MinIO (processed-data/ bucket), layer2.clean.ready Kafka event, DB run records + lineage

  Layer 3 — Ontology & Intelligence                                                                                                               
                                                            
  Port: 8003
  Purpose: Map processed data into a typed entity graph, compute risk scores, detect anomalies, run automated actions, maintain temporal history.
                                                                                                                                                  
  Implemented components:
                                                                                                                                                  
  - FastAPI API (api/main.py) — 9 route groups: objects, search, graph, intelligence, actions, timeline, health, ingest, schema                   
  Elasticsearch index + Redis cache invalidation + Kafka event emission on every write                                                    
  - BatchIngestor (ingestion/batch_ingestor.py, 219 lines) — loads Parquet from MinIO → maps → validates → writes via Funnel; emits               
  layer3.ingest.complete to Kafka on completion

  (acks=all, retries=3) for layer3.ingest.complete                                                                                             
  - Schema registry — ObjectTypeRegistry, LinkTypeRegistry, PropertyRegistry, InterfaceRegistry, VersionManager backed by 5 PostgreSQL tables;    
  seeded on API startup                                                                                                                       
  - 12 ontology object types — Company, Director, Address, Alert, Event, LegalCase, InsolvencyProceeding, Project, RegulatoryAction,              
  RegulatoryBody, GovernmentEntity (with Indian-specific types: CIN_Type, Currency_INR, IndianDate_Type, RiskScore_Type)            
  - 4 link type modules — Corporate (8 links: DIRECTED, OWNS, SUBSIDIARY_OF, REGISTERED_AT, SHARES_DIRECTOR_WITH, SHARES_ADDRESS_WITH,            
  COMMON_BENEFICIAL_OWNER, HAS_EVENT), Regulatory, Project, Inference (inferred links)                                                
  - ObjectMapper — maps raw Parquet DataFrames to ontology objects by source name                                                                 
  - RelationshipMapper — extracts director-company links from director DataFrames
  - SchemaValidator — validates records against type definitions before write                                                                     
  - 5 anomaly detectors — DirectorProliferationDetector, AddressClusteringDetector, CIRPContagionDetector, FilingComplianceDetector,              
  RegulatoryRecidivismDetector                                                                                                                    
  - Risk scoring engine — RiskScoringEngine orchestrates CompanyScorer, DirectorScorer, ProjectScorer, GroupScorer; CompanyScorer.compute_score() 
  pulls Neo4j for regulatory actions, directors, projects; has sync score() method for props-only fast path                                       
  - 6 graph intelligence modules — NetworkMapper, ClusterDetector, InfluenceScorer, PathFinder, TemporalAnalyzer, SharedAttributeAnalyzer         
  - predictProjectCompletionProbability (kinetic/functions/project_probability.py) — heuristic v0.3 with FEATURE_SCHEMA_VERSION constant; factors:
   schedule delay (non-linear), land acquisition, cost overrun, project status, CIRP on owner, regulatory actions                                 
  - WorkflowEngine (kinetic/workflow_engine.py) — 5 registered action types: FlagCompanyForReview, UpdateProjectStatus,                           
  MarkRegulatoryActionResolved, CreateIntelligenceAlert, MergeCompanyObjects; role-gated                                                          
  - ChangeDetector (timeline/change_detector.py) — uses deepdiff to diff object states; detect() / compute_diff() methods                         
  - TimelineService, EventSourcingService — temporal event tracking and audit log                                        
  - RBAC — RBACMiddleware, ObjectSecurityFilter, role hierarchy (analyst, data_steward, compliance_head, platform_administrator, system)          
  - AuditLogger — all write operations logged                                                                                                     
  - 4 health monitors — OntologyHealth, OrphanDetector, DuplicateSurface, ImpossibleStateDetector                                                 
  - Storage layer — Neo4jStore (MERGE), ElasticsearchStore (index), CacheStore (Redis TTL), EventStore, IncrementalIndexer                        
  - Schema registry migration — 1 SQL file (6 tables: object_types, property_definitions, link_types, interfaces, schema_versions,                
  data_source_mappings)                                                                                                                           
                                                                                                                                                  
  Inputs: Processed Parquet from MinIO, HTTP POST to /api/v1/ingest                                                                               
  Outputs: PostgreSQL (ontology_objects, ontology_links, schema tables), Neo4j graph (MERGE), Elasticsearch indices, Redis cache,                 
  layer3.ontology.changes + layer3.ingest.complete Kafka events

  Layer 4 — Graph Intelligence

  Port: 8004
  Purpose: Advanced pre-computed graph analytics — centrality, community detection, path intelligence, CIRP precursor scoring, temporal analysis.
  Reads from Neo4j/PostgreSQL, writes pre-computed results to L4 PostgreSQL tables.                                                               
   
  Implemented components:                                                                                                                         
                                                            
  - FastAPI API (api/main.py) — 8 route groups: network, paths, clusters, attributes, influence, subgraph, temporal, queries; CORS wide-open (*)  
  Redis keys on entity change; runs as asyncio background task on startup                                                                    
  - NetworkMapper — GraphNode, GraphEdge, NetworkMap dataclasses; builds in-memory network subgraphs from Neo4j queries                           
  - TraversalEngine — TraversalStep class; BFS/DFS traversal with hop limits                                           
  - PruningEngine — reduces large graphs for API responses                                                                                        
  - ShortestPathFinder — PathResult dataclass; Cypher-based shortest path                                                                         
  - AllPathsFinder — MultiPathResult; all paths with max hop limit                                                                                
  - PathScorer — ScoredPath dataclass; scores connection paths by risk signal density                                                             
  - NarrativeGenerator — uses Anthropic claude-sonnet-4-6 (AsyncAnthropic client) with Redis caching to produce plain-English path narratives;    
  gracefully disabled if ANTHROPIC_API_KEY not set                                                                                                
  - 6 clustering algorithms — LouvainDetector/LouvainClusterDetector, LabelPropagationDetector, AddressClusterDetector, DirectorClusterDetector,  
  RegulatoryClusterDetector, TemporalClusterDetector; all use Neo4j GDS projections                                                               
  - 6 influence/centrality scorers — PageRankComputer/PageRankScorer, BetweennessCentralityComputer/BetweennessCentralityScorer,                  
  DegreeCentralityComputer, RegulatoryExposureComputer, RiskWeightedComputer, InfluenceAggregator                                               
  - 3 shared-attribute detectors — SharedDirectorDetector/DirectorConnectionDetector, SharedAddressDetector/AddressConnectionDetector,            
  SharedOwnerDetector, SharedAttributeBatchProcessor                                                                                  
  - PrecursorModel (temporal/precursor_model.py) — CIRPRiskAssessment dataclass; rule-based scoring using 13 signals (director turnover,          
  regulatory actions, legal cases, address clustering, offshore directors, etc.) with CRITICAL/HIGH/MEDIUM/LOW bands and explicit Phase 2 XGBoost
  upgrade path                                                                                                                                    
  - VelocityAnalyzer, RotationTracker — director rotation rate and velocity analysis for temporal signals
  - EventCorrelator, SnapshotEngine — graph state snapshots and event correlation                                                                 
  - SubgraphExtractor, SnapshotBuilder, SubgraphDiffer — named subgraph extraction, snapshots, diffing                                            
  - SubgraphTemplate — predefined subgraph patterns                                                                                               
  - QueryParser — ParsedQuery dataclass; natural language query parsing using Anthropic API (disabled without API key)                            
  - QueryComposer — routes parsed queries to appropriate analysis subsystems                                                                      
  - GDS client (core/gds_client.py) — Neo4j Graph Data Science API wrapper                                                                        
  - Neo4j compat shim — _Neo4jClientCompat class (exposes neo4j_client singleton with run_query/run_write)                                        
  - Airflow DAG (l4_nightly_intelligence_batch.py) — runs at 1am daily; sequential phases: create_projection → betweenness → pagerank → degree →  
  louvain → label_propagation → address_clusters → director_clusters → precursor_model                                                            
  - L4 schema migration — 1 SQL file: l4_influence_scores, l4_cluster_memberships, l4_address_clusters, l4_subgraph_definitions, l4_batch_runs    
  tables                                                                                                                                          
  - API key auth — optional, warns on startup if not set                                                                                          
                                                            
  Inputs: Neo4j graph (reads), l3_* PostgreSQL tables (reads), Kafka (layer3.ontology.changes, layer3.ingest.complete)                            
  Outputs: l4_influence_scores, l4_cluster_memberships, l4_address_clusters PostgreSQL tables; Redis cache (l4:* namespace); HTTP JSON API        
  responses

  5. PIPELINE & PROCESSING SYSTEM
                                                                                                                                                  
  Definition format: YAML files, stored in layer2_pipeline/pipelines/{client}/.
                                                                                                                                                  
  YAML structure:                                           
  pipeline_id: infracore_company_master                                                                                                           
  version: "1.0"                                            
  client_id: infracore                                                                                                                            
  lineage_config:     
    entity_type: company                                                                                                                          
    entity_id_column: cin                                   
  cross_batch_dedup:                                                                                                                              
    enabled: true                                                                                                                                 
    key_columns: [cin]
  steps:                                                                                                                                          
    - step_id: normalize_cin                                                                                                                      
      transform_type: normalize_cin
      depends_on: []                                                                                                                              
      config: {column: cin, reject_invalid: false}                                                                                                
      quality_rules:                              
        - rule_id: cin_not_null                                                                                                                   
          rule_type: not_null                               
          column: cin                                                                                                                             
          failure_policy: reject                            
      on_error: fail                                                                                                                              
                                                            
  Execution: PipelineExecutor.execute() — never raises, all errors captured in DB.                                                                
                                                                                                                                                  
  DAG system:                                                                                                                                     
  - Uses networkx for topological sort and cycle detection (falls back to DFS if networkx missing)                                                
  - Computes critical path for monitoring                                                                                                         
  - Step definitions: step_id, transform_type, config, depends_on, quality_rules, on_error
  - Transform registry: 28+ transforms keyed by string type name, auto-registered at import                                                       
                                                                                                                                                  
  Scheduling:                                                                                                                                     
  - Layer 1: Airflow extraction_dag.py                                                                                                            
  - Layer 2: Airflow layer2_pipeline_dag.py — */15 * * * *, max 4 concurrent runs, retries 2×, exponential backoff, max retry 30min               
  - Layer 4: Airflow l4_nightly_intelligence_batch.py — 0 1 * * *, max 1 concurrent run, sequential phases via XCom                
                                                                                                                                                  
  Production pipeline definition delivery: Pipeline YAML must be loaded into the l2_pipeline_definitions DB table before execution. No hot-reload 
  or file-watching; DB is source of truth at runtime.                                                                                             
                                                                                                                                                  
  Currently defined pipelines: 2 (company_master, director_mapping).

  9. KNOWN GAPS & RISKS                                     
                                                                                                                                                  
  Critical:
  1. L2→L3 broken link: layer2.clean.ready Kafka topic is published by Layer 2 but nothing consumes it. Layer 3 ingestion must be triggered       
  manually. This breaks the automation chain.                                                                                                     
  2. DB migrations not automated: 7 SQL migration files across layers with no runner (alembic, flyway, or script). First deployment requires
  manual psql execution in the correct order.                                                                                                     
  3. Single PostgreSQL instance: Layers 1, 2, and 3 share one PostgreSQL DB. No connection pooling (PgBouncer). Under load, this is a scalability 
  bottleneck and a failure point.                                                                                                                
  4. requirements.txt version drift: Root requirements.txt pins kafka-python==2.0.2 (broken on Python 3.12), sqlalchemy==1.4.49 (system has       
  2.0.x), pandas==2.2.2 (system has 3.0.x), fastapi==0.104.0 (system has 0.136.x). The installed packages are newer than pinned versions — 
  deployments from pip install -r requirements.txt will install incompatible versions and fail.                                                   
  5. GSTIN checksum disabled: validate_gstin() uses pattern-only validation; the checksum algorithm in GSTINValidator._verify_checksum() produces
  wrong results for known-valid test GSTINs. The class method should not be used directly.                                                        
  6. Layer 4 CORS wide-open: allow_origins=["*"] in layer4/api/main.py — anyone on the network can call L4 API endpoints without credentials.     
   
  Architectural weaknesses:                                                                                                                       
  7. No .env file in repo: .env is referenced throughout but not committed. Docker compose and configs have hardcoded dev defaults that would be
  exposed in a misconfigured deployment.                                                                                                          
  8. API key auth is optional: Both Layer 1 and Layer 4 warn but do not enforce auth. Production requires API_KEY env var to be set.
  9. Layer 3 → 4 trigger is nightly-only: Real-time L3 changes invalidate L4 Redis cache instantly, but pre-computed L4 intelligence (centrality, 
  clusters, CIRP scores) only refreshes at 1am. Newly ingested entities are invisible to L4 analytics until next batch.                           
  10. Neo4j GDS dependency: Layer 4 clustering and centrality algorithms require Neo4j Graph Data Science plugin. Not all Neo4j 5.14 images       
  include GDS; must use the enterprise/GDS-enabled image.                                                                                         
  11. deepdiff dependency in L3: ChangeDetector requires deepdiff package, not listed in root requirements.txt.
  12. Anthropic SDK in L4 requires API key at runtime: NarrativeGenerator and QueryParser import anthropic at module level — the package must be  
  installed even if the API key is not set.                                                                                                       
                                                                                                                                                  
  Silent failure risks:                                                                                                                           
  13. Kafka publish failures are silently swallowed: All Kafka producers log at WARNING/DEBUG and return False/None. If Kafka is down, data keeps
  flowing but downstream layers receive no events — no alerting, no dead letter queue.                                                            
  14. Cross-batch fingerprint cap: _persist_fingerprints() silently caps at 50,000 fingerprints per run. Batches exceeding 50,000 unique records
  will have partial fingerprint coverage without any error raised.                                                                                
  15. L3 BatchIngestor triggered manually: No guaranteed trigger from L2. If the operator forgets to run ingestion, Layer 3 silently falls behind
  Layer 2.

  1. Ingest and profile raw data from 14 connectors (10 generic + 4 Indian), detect schema fingerprint, write Parquet to MinIO, publish           
  Kafka/Redis events.                                                                                                                             
  2. Execute YAML-defined pipelines — 28+ transforms, quality rules, exact/fuzzy/cross-batch deduplication, field-level lineage, error quarantine 
  — on Parquet DataFrames.                                                                                                                        
  3. Normalise Indian corporate identifiers — CIN, DIN, PAN, GSTIN, IFSC, state codes, PIN codes, Indian number formats (crore notation), Indian
  dates (8 formats including MCA21 compact).                                                                                                      
  4. Map processed data into a typed ontology graph — 12 object types, 8+ link types, schema-validated, written atomically to PostgreSQL + Neo4j +
   Elasticsearch + Redis.                                                                                                                         
  5. Score company, director, and project risk using Neo4j-backed signal queries (regulatory actions, CIRP status, director disqualification,
  offshore exposure).                                                                                                                             
  6. Predict CIRP (insolvency) risk using a 13-signal rule-based model with CRITICAL/HIGH/MEDIUM/LOW bands.
  7. Detect anomalies — director proliferation, CIRP contagion, filing compliance failures, address clustering, regulatory recidivism.            
  8. Run graph analytics nightly — Louvain/LabelPropagation communities, PageRank/Betweenness centrality, shared director/address detection,      
  temporal velocity analysis.                                                                                                                     
  9. Find connection paths between corporate entities with risk signal scoring.                                                                   
  10. Generate plain-English narratives of entity connections (requires Anthropic API key).                                                       
  11. Execute role-gated actions — flag companies, update project status, merge duplicate objects, create intelligence alerts.

  - No frontend — no dashboard, no UI of any kind exists in the repository

  environment                                                                                                                              
  - L2→L3 trigger gap means full pipeline automation requires manual intervention at the L3 boundary                                              
  - All intelligence is rule-based heuristics; no ML models are trained (Layer 5 XGBoost is planned, not implemented)
  - NL query and narrative features require Anthropic API key

  Prerequisites: Docker, Docker Compose, .env file          

  Step 1: Create .env                                                                                                                             
  POSTGRES_DB=infracore
  POSTGRES_USER=infracore                                                                                                                         
  POSTGRES_PASSWORD=infracore_dev_password                  
  MINIO_ACCESS_KEY=infracore_minio        
  MINIO_SECRET_KEY=infracore_minio_secret                                                                                                         
  KAFKA_BOOTSTRAP_SERVERS=kafka:9092     
  NEO4J_PASSWORD=infracore123                                                                                                                     
                                                            
  Step 2: Start infrastructure                                                                                                                    
  cd /opt/php74/satorix/infracore_foundry                                                                                                         
  docker compose up -d postgres minio redis kafka neo4j elasticsearch airflow-init
  docker compose up -d  # start all services                                                                                                      
                                                                                                                                                  
  Step 3: Run database migrations (no auto-runner exists — manual)                                                                                
  # Layer 1                                                                                                                                       
  psql -U infracore -d infracore -f layer1_ingestion/registry/migrations/001_initial_schema.sql
  psql -U infracore -d infracore -f layer1_ingestion/registry/migrations/002_column_fixes.sql                                                     
                                                                                                                                                  
  # Layer 2                                                                                                                                       
  psql -U infracore -d infracore -f layer2_pipeline/migrations/001_l2_tables.sql                                                                  
  psql -U infracore -d infracore -f layer2_pipeline/migrations/002_l2_dataset_versions.sql                                                        
  psql -U infracore -d infracore -f layer2_pipeline/migrations/003_l2_batch_fingerprints.sql                                                      
                                                                                                                                                  
  # Layer 3                                                                                                                                       
  psql -U infracore -d infracore -f layer3_ontology/schema_registry/migrations/001_ontology_schema.sql                                            
                                                                                                      
  # Layer 4
